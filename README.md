# Предиктор задержек наземного транспорта

ИИ-система раннего прогнозирования отклонений от графика движения: за **10-15 минут**
до фактического наступления задержки система оценивает её величину, вероятность
опоздания, определяет паттерн сбоя и показывает это диспетчеру на карте с цветовой
индикацией риска.

MAE на размеченном test - **47.4 с** против **93.4 с** у наивной подсказки
`cur_dev_s`, то есть модель ошибается вдвое меньше. Это удвоение достигнуто на
141 признаке; ниже приведено, как оно считается и что именно проверяемо.
Скор платформы на скрытом validate-срезе команда не измеряла и не заявляет:
его формула задана организаторами, а ground truth скрыт.

## Архитектура

Три сервиса, одна строгая зависимость: `dashboard → backend → ml`. Модель
находится в отдельном контейнере, и Backend к ней не имеет доступа ни по
импорту, ни по файлу.

```
  ┌───────────────┐   HTTP    ┌────────────────────┐   HTTP    ┌──────────────────┐
  │  Дашборд      │──────────►│  Backend           │──────────►│  ML service      │
  │  React :8080  │  /api     │  FastAPI  :8000    │ /predict  │  FastAPI :8001   │
  └───────────────┘           │                    │  JSON     │                  │
                              │  • приём NDTP      │           │  • признаки      │
 ┌──────────────┐  NDTP/TCP   │  • оркестрация     │           │  • загрузка      │
 │ Эмулятор NDTP│────────────►│  • отклонение ТС   │           │    модели        │
 │ или validate/│   :9201     │  • каскад по сети  │           │  • CatBoost      │
 └──────────────┘             │  • микробатчинг    │           │  • паттерны      │
                              │  • API, метрики    │           │  • калибровка    │
                              └────────────────────┘           └──────────────────┘
```

| Сервис | Порт | Код | Роль |
|---|---|---|---|
| **ML service** | 8001 | `ml-service/service.py`, `src/predictor.py`, `src/patterns.py` | признаки, загрузка модели, inference, калибровка, детекторы |
| **Backend** | 8000 | `backend/main.py`, `src/runtime.py`, `src/ndtp*.py`, `src/cascade.py`, `src/batching.py`, `src/deviation.py`, `src/ml_client.py` | приём NDTP, оркестрация, каскад, отклонение ТС, API, метрики |
| **Дашборд** | 8080 | `dashboard/src/` | React-приложение: карта, индикация риска, карточка инцидента |

### Граница проходит по inference

Backend **не импортирует** `src.predictor` и **не устанавливает** CatBoost.
Это проверяемо, а не декларативно:

```bash
docker run --rm --entrypoint python predictor-backend -c \
  "import importlib.util as u, sys, backend.main; \
   print('catboost:', u.find_spec('catboost') is not None, \
         '| loaded:', 'catboost' in sys.modules)"
# catboost: False | loaded: False
```

Единственное, что Backend знает о модели, - адрес `ML_SERVICE_URL`.

Общий для двух сервисов модуль - `src/schedule_index.py` (разбор
`schedule_plan.csv`, геометрия остановок). Это обычная библиотека в монорепозитории,
а не связь на уровне сервисов: она не содержит ни CatBoost, ни inference, и
проверяется тестом на «импорт не тянет ML-стек».

### Один batch-эндпоинт вместо single + batch

У ML service один эндпоинт предсказания - `POST /predict`, принимающий массив
точек. Отдельного single-эндпоинта нет сознательно: стоимость построения
признаков почти не зависит от числа строк (49.7 мс на 1 точку против 5.1 мс/строку
на 32), поэтому запрос на одну точку - это тот же код с массивом длины один.
Микробатчинг в Backend склеивает параллельные запросы и делает **один** вызов;
в тесте 48 запросов схлопываются в 18 вызовов к ML service.

### Что происходит, когда ML service недоступен

| Слой | Поведение |
|---|---|
| Клиент | таймаут (connect отдельно от read), 1 повтор, circuit breaker: 3 ошибки подряд → 10 с быстрых отказов без обращения к сети |
| Клиент | ответ не-JSON, неверная форма, `prediction = null` → `MlServiceError(kind="malformed")`, а не «принять как есть» |
| `/predict`, `/generate_submission` | `503` с указанием причины (`unavailable` / `timeout` / `loading`) |
| `/stream/status`, `/cascade`, `/ndtp/status`, `/models` | продолжают работать; live-панель сохраняет позиции, двери и измеренное `cur_dev_s` |
| Реплей | теряет прогноз этого тика, часы идут дальше; счётчики в `/metrics` |
| `/health` | `degraded` + причина, но **200**: контейнер остаётся healthy, чтобы его не перезапускал Docker |

Проверено на живом стеке: при остановленном контейнере `ml` backend остаётся
healthy, `/predict` отдаёт 503, `/cascade` и `/stream/status` — 200, а после
возврата `ml` восстановление происходит само.

### Обучение осталось офлайн

ML service **не обучает** модель - он обслуживает inference. Переобучение
поднятого артефакта - отдельная задача со своим образом `ml/Dockerfile`
(`baseline_v2.py`), который в compose не входит: `train/test/labels` не
коммитятся, и в рантайме они не нужны.

```bash
docker build -f ml/Dockerfile -t predictor-train .
docker run --rm -v "$(pwd)/dataset:/app/dataset:ro" predictor-train
```

`ml/baseline.py` (5 признаков на Polars) - историческая база для сравнения, в
контур не входит.

## Быстрый старт

### Требования

- Docker + Docker Compose v2
- ~2 ГБ свободной памяти
- Ключ карт 2ГИС (см. ниже)

### Запуск

```bash
git clone https://github.com/Loading696/public-transport-predictor
cd public-transport-predictor

# 1. Ключ карт. Скопируйте пример, ключ уже вписан:
cp dashboard/.env.example .env
#    редактируем: VITE_TWOGIS_API_KEY=dd2f8518-b305-4440-b459-0febf531ede3
#    Или получить новый бесплатный ключ: https://console.2gis.ru/ → Projects → API keys

# 2. Запуск
docker compose up --build
```

Через ~2-3 минуты сборки:

| Адрес | Что это |
|---|---|
| **http://localhost:8080** | **Дашборд диспетчера** |
| http://localhost:8000/docs | Swagger - интерактивная документация API |
| http://localhost:8000/health | Готовность backend и ML-сервиса |
| http://localhost:8000/metrics | Метрики времени выполнения и состояние ML |

Поднимаются три сервиса: `ml` (модель и inference, порт 8001 - внутренний, наружу
не публикуется), `backend` (8000) и `dashboard` (8080). Backend ждёт
`service_healthy` у `ml`, поэтому к моменту старта дашборда модель уже загружена.

Проверка, что всё поднялось:

```bash
curl http://localhost:8000/health
# {"status":"ok","model":"http://ml:8001","features":141,"validate_points":151,
#  "ml":{"status":"ok","service":"predictor-ml","model_loaded":true,...}}
```

Если ML-сервис не поднялся, backend всё равно будет доступен, а `/health`
покажет `degraded` с причиной - см. раздел про деградацию.

**Дашборд запустится сразу** - в репозиторий включён `dataset/validate/`, поэтому
реплей стартует без дополнительных действий. Опорный сценарий: реплей валидационного
периода со скоростью ×60; карта, прогнозы и карточка инцидента заполняются по мере
продвижения модельного времени.

### Порт для карт

Ключ 2ГИС обязателен: без него вместо карты выводится поясняющая страница. Приложение
поддерживает Яндекс и Google как запасные провайдеры - ключ задаётся в `.env`
переменными `VITE_YANDEX_API_KEY` / `VITE_GOOGLE_MAPS_API_KEY`.

## Инструкция для жюри: как подать поток

Система работает с двумя источниками телематики. Оба проверялись вживую.

### Сценарий A. Исторический датасет (рекомендуется для быстрого старта)

Ничего делать не нужно - датасет `dataset/validate/` уже в репозитории, реплей
стартует автоматически при `docker compose up`.

Управление потоком - в сайдбаре дашборда (ползунок скорости ×1…×600 и кнопка
перезапуска) или через API:

```bash
# ускорить до максимума
curl "http://localhost:8000/stream/status?speed=600"

# перезапустить поток с начала
curl "http://localhost:8000/stream/status?reset=true"
```

### Сценарий B. Живой эмулятор NDTP (демонстрация приёма потока)

Показывает непрерывный приём и парсинг бинарного протокола NDTP по TCP.

```bash
# 1. Загрузить образ эмулятора.
#    ВАЖНО: файл ndtp-telemetry-emulator.tar НЕ входит в репозиторий
#    (*.tar в .gitignore) и поставляется организаторами вместе с датасетом.
#    Без него сценарий B не запускается; сценарий A работает из коробки.
docker load -i dataset/ndtp-telemetry-emulator.tar

# 2. Поднять стенд вместе с эмулятором
docker compose --profile emu up --build

# 3. Сконфигурировать эмулятор: отправлять на наш приёмник TCP 9201
curl -X POST http://localhost:18080/api/config \
     -H "Content-Type: application/json" \
     -d @ndtp-emu-config.json
```

Приёмник NDTP при этом поднимается всегда и не зависит от эмулятора: без
внешнего источника он просто ждёт соединений, а счётчики `/ndtp/status`
остаются нулевыми. Самостоятельно проверить разбор протокола можно без сети -
тест `py ml/test_ndtp.py` гоняет handshake, CRC-16/Modbus, ячейки и TCP-цикл
на синтетических кадрах.

Ожидаемый ответ эмулятора - эхо конфига с `targetPort: 9201`. Через несколько секунд
живой поток появится в дашборде (вкладка **📡 Live NDTP**).

Проверка, что кадры действительно приходят и разбираются:

```bash
curl http://localhost:8000/ndtp/status
```
```json
{"enabled":true,"port":9201,"buffered_rows":118,"connections":1,"handshakes":1,
 "realtime":118,"rows":118,"crc_errors":0,"frame_errors":0,"door_open_frames":118}
```

Что означают счётчики:

- `connections` / `handshakes` - TCP-соединения и успешные `NPH_SGC_CONN_REQUEST`
- `realtime` / `rows` - принято пакетов `NPH_SND_REALTIME` и декодировано строк
- `crc_errors` - отброшено по CRC-16/Modbus (должно быть **0**)
- `door_open_frames` - кадры, где распознан статус дверей

**Маппинг юнитов на расписание.** Прогноз возможен только когда юниту известны
маршрут и целевая остановка. Задайте соответствие переменной окружения:

```bash
UNIT_TR_MAP='{"1166336": 131672}' docker compose up
```

Без маппинга юнит виден на карте с телеметрией, но помечается «нет расписания для ТС»
и прогноза не получает - это честная деградация, а не сбой.

### Что подавать, если нужно оценить качество прогноза

Одна команда строит финальный CSV из подготовленных validate-данных и сразу
проверяет результат. Код возврата ненулевой, если файл невалиден, поэтому
команду можно использовать как предсабмит-гейт.

```bash
# локальный пайплайн, без запущенных сервисов -> ./submission.csv + отчёт валидации
py ml/make_submission.py

# тот же файл через работающий стек: dashboard -> backend -> ml
py ml/make_submission.py --via http --url http://127.0.0.1:8000

# только проверить уже существующий файл, ничего не считая
py ml/make_submission.py --check-only --out submission.csv
```

Положить файл в контейнер и скачать обратно (сервисы уже подняты):

```bash
curl http://localhost:8000/generate_submission      # -> /app/out/submission.csv в volume submissions
docker cp asdasd-backend-1:/app/out/submission.csv ./submission.csv
py ml/make_submission.py --check-only --out submission.csv
```

#### Пайплайн целиком

```
dataset/validate/points.csv        что предсказывать: sample_id, T, остановка, target_time
dataset/validate/traffic.csv       телеметрия, причинно обрезанная по T каждой точки
dataset/validate/schedule_plan.csv план
        |
        |  предобработка - ml-service/service.py
        |    нормализация, разбор WKT-геометрии, обрезка event_time <= T
        |    (строка телеметрии с будущим T не попадает в признаки)
        v
        |  inference - CatBoost (задержка) + risk / class / калиброванный p_late
        |    + детекторы паттернов ( dwell, заторы, отказы, микробатчинг)
        v
        |  запись - ml/submission.py
        |    единственный владелец формата, валидирует файл сразу после записи
        v
submission.csv    sample_id;prediction, ровно одна строка на точку,
                  в порядке dataset/validate/points.csv
```

#### Формат submission.csv

| | |
|---|---|
| разделитель | `;` |
| заголовок | `sample_id;prediction` |
| строк данных | 151 на validate, по одной на точку из `points.csv` |
| порядок | строго как в `points.csv` - площадка сопоставляет и по позиции |
| `prediction` | конечное число, `%.6f`, единицы - секунды |
| кодировка | UTF-8, без BOM, без index-колонки |

Отрицательные значения допустимы: модель предсказывает задержку, а досрочный
приезд — это отрицательная задержка. Границы «правдоподобного» диапазона
(±86400 с, сутки) в `ml/submission.py` заведены как защита от багов, а не как
фильтр разумных значений.

#### Что проверяет валидатор

`py ml/make_submission.py` (и любой другой вызов `ml/submission.py`) проверяет и
**не даёт записать** файл, если: число строк не совпадает с `points.csv`;
`sample_id` повторяются, пустые, отсутствуют или присутствуют лишние; строки
переставлены; `prediction` не число / `NaN` / `Inf`; точка вне горизонта
`target_time_begin - T` в `(600, 900]` секунд. Итоговый отчёт печатается всегда:

```
  submission
    file                 .../submission.csv
    rows                 151 / 151 expected
    unique sample_id     151
    duplicates           0
    ...
  predictions
    min / max            -218.532 / 420.003 s
    mean                 63.396 s
```

Формат живёт в одном месте — `ml/submission.py`. Его используют HTTP-эндпоинт
`/generate_submission`, офлайн-пайплайн `ml/ml_pipeline.py`, обучение
`ml/baseline_v2.py` и `ml/make_submission.py`, поэтому переобученная модель не
может записать файл другого вида, чем задеплоенная.

## Где смотреть прогнозы, алерты и метрики

### Дашборд - http://localhost:8080

| Блок | Что показывает |
|---|---|
| **KPI-панель** | модельное время, скорость потока, обработанные точки, число ТС в прогнозе |
| **Карта** | маршрутная сеть; маршруты окрашены по уровню риска: 🟢 в графике / 🟡 под риском / 🔴 опоздание. Синие маркеры - живой поток NDTP, отдельно отмечается состояние дверей |
| **Карточка инцидента** | ТС с максимальным прогнозом: величина опоздания, **калиброванная вероятность** `P(опоздание > 120 с)`, плановое и прогнозное время прибытия, целевая остановка с адресом, текущий и целевой участки, **причина сбоя** с указанием статуса сигнала, рекомендация диспетчеру |
| **Каскад задержки** | распространение опоздания по плановой сети: ΔETA по остановкам и остановка, на которой парк «поглотит» задержку |
| **Табло расписания** | план по каждому ТС с отметкой «время прошло / следующая / по плану» и прогнозом на целевой остановке |
| **Ближайшие прибытия** | сводка по всем активным ТС, отсортированная по времени |

### Метрики - http://localhost:8000/metrics

```json
{
  "endpoints": {"/predict": {"count": 52, "mean_ms": 202.1, "max_ms": 691.0, "errors": 0}},
  "inference": {"count": 52, "mean_ms": 199.8, "rows_per_call": 1.54},
  "batching": {"batches": 17, "jobs": 52, "jobs_per_batch": 3.06, "rows_per_batch": 4.71},
  "model": {"features": 141, "traffic_rows": 105945, "predict_points": 151}
}
```

Ключевое поле - `batching.jobs_per_batch`: сколько параллельных запросов
объединилось в один вызов модели. Значение > 1 означает, что микробатчинг работает.

## API

Полная интерактивная спецификация - **http://localhost:8000/docs** (Swagger UI),
машиночитаемая - `/openapi.json`.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/predict` | пакетный прогноз по своим точкам и телеметрии (backend → ML service) |
| `GET` | `/stream/status` | снимок витрины: прогнозы, позиции, инцидент, живой поток |
| `GET` | `/cascade` | каскадное распространение задержки по плановой сети |
| `GET` | `/ndtp/status` | счётчики TCP-приёмника NDTP |
| `GET` | `/generate_submission` | пересчитать `submission.csv` |
| `GET` | `/metrics` | метрики задержек, батчинга и состояния ML-сервиса |
| `GET` | `/health` | готовность backend и ML-сервиса |
| `GET` | `/models`, `/v1/models` | адрес и метаданные модели, которые держит ML-сервис |

`/predict` и `/generate_submission` отвечают `503`, если ML service недоступен;
остальные продолжают работать. Подробности - в разделе «Что происходит, когда ML
service недоступен».

Собственный API ML-сервиса (Swagger - на `http://localhost:8001/docs`, в compose
порт не публикуется - он внутренний):

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | `status`, `model_loaded`, число признаков, ошибка загрузки |
| `GET` | `/models` | список имён признаков и признак готовности |
| `POST` | `/predict` | батчевый inference: `{points, telemetry}` → `{count, predictions}` |

### Пример запроса прогноза

```bash
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"points":[{"sample_id":"demo_1","tr_id":131672,
        "T":"2026-01-06 03:35:00","target_stop_id":53700172828,
        "target_time_begin":"2026-01-06 03:50:00","cur_dev_s":274.0}],
       "telemetry":[{"tr_id":131672,"event_time":"2026-01-06 03:34:50",
        "lon":37.8596,"lat":55.7302,"speed":0.0,"location_valid":true}]}'
```

```json
{"count":1,"predictions":[{
  "sample_id":"demo_1","tr_id":131672,
  "prediction":137.34,
  "p_late":0.62,
  "target_class":"late","risk":"late",
  "recommendation":"скорректировать интервал на маршруте",
  "pattern_events":[{"type":"dwell","role":"weak_signal","confidence":0.94,
                     "reason":"простой: средняя скорость 0.0 км/ч за 5 мин"}]}]}
```

## ML-ядро

### Модель

CatBoost-регрессия задержки, **141 признак**, `loss_function=MAE`.

| Метрика | Модель | Наивная подсказка `cur_dev_s` |
|---|---|---|
| MAE на test | **47.4 с** | 93.4 с |
| Относительно наива | **×1.97** | ×1.00 |

Модель превосходит подсказку более чем вдвое. Наивный прогноз «задержки нет»
(нулевой) заведомо хуже подсказки - то есть качество не обеспечено константой.
Обе цифры получены на одном и том же размеченном test; воспроизводятся командой
`py ml/baseline_v2.py`. Скор платформы на скрытом validate-срезе не измерялся:
формула скора задана организаторами, а ground truth скрыт, поэтому в таблице
его нет - сравнение с ним было бы непроверяемым числом.

### Вероятность опоздания

Изотоническая калибровка `P(задержка > 120 с | прогноз)`, обученная на честном
holdout (n=353).

| Метрика | Значение | Интерпретация |
|---|---|---|
| **Brier score** | **0.066** | против 0.184 у константного прогноза - почти втрое лучше |
| Доля опозданий в test | 0.244 | базовая ставка |

Кривая лежит в `ml/prob_cal.json` и применяется к каждому прогнозу, поле `p_late`
в ответе API и в карточке инцидента.

### Детекторы паттернов сбоя

Измеренное качество на test (86 фактических опозданий). Роли присвоены по
фактическому качеству, а не предположительно:

| Детектор | Precision | Recall | Роль | Интерпретация |
|---|---|---|---|---|
| `backlog` | 0.46 | 0.51 | **strong_signal** | накопленное отставание - единственный рабочий предиктор |
| `dwell` | 0.24 | 0.19 | weak_signal | простой: на уровне базовой ставки, слабый индикатор |
| `speed_drop` | 0.25 | 0.07 | weak_signal | просадка скорости: слабый, редкий |
| `stale` | 0.00 | 0.00 | **data_quality** | не предиктор задержки, а флаг недостоверности телеметрии |

Событие приходит в API как `{type, role, confidence, reason}`. Карточка инцидента
показывает причину **вместе с её статусом** - так что «слабый сигнал» никогда не
выдаётся за установленный факт.

#### Причина ≠ качество данных

События делятся на две категории, и они **никогда не ранжируются между собой**:

| Категория | События | Что означает | Как ранжируется |
|---|---|---|---|
| **причина сбоя** | `backlog`, `dwell`, `speed_drop` | почему ТС опаздывает | `strong` → `weak`, затем по `confidence` |
| **качество данных** | `stale` | насколько можно доверять телеметрии | отдельно, как предупреждение |

`stale` с precision 0.00 не может быть причиной задержки. Раньше `cause_from_events`
складывал все события в один список и сортировал по роли с `data_quality` **на
первом месте**, поэтому при любом совпадении `stale` + реальный паттерн
причиной становилась «телеметрия недостоверна», а настоящая причина терялась.
Теперь разделение выполняется в `patterns.split_events()`:

| События | Причина | Дополнительно | Качество |
|---|---|---|---|
| `stale` + `backlog` | **backlog** (strong) | — | ⚠ stale |
| `stale` + `dwell` | **dwell** (weak) | — | ⚠ stale |
| `stale` + `speed_drop` | **speed_drop** (weak) | — | ⚠ stale |
| `backlog` + `dwell` + `speed_drop` | **backlog** | dwell, speed_drop | ok |
| только `stale` | причина **не определена** | — | ⚠ stale |
| ничего | неизвестна (эвристика) | — | ok |

Уверенность `stale` на это не влияет: даже `confidence = 1.0` не вытесняет
`backlog`. Сильный сигнал всегда сильнее слабого независимо от `confidence`,
а все прочие сработавшие паттерны не выбрасываются, а уходят в
`additional_causes`.

Ответ `/stream/status` разделяет эти вещи явно:

```json
{"cause": "накопленное отставание от графика сохраняется к целевой остановке",
 "cause_role": "strong_signal", "cause_type": "backlog",
 "additional_causes": [{"type": "dwell", "role": "weak_signal",
                        "confidence": 0.61, "reason": "простой: средняя скорость 1.0 км/ч"}],
 "telemetry_quality": {"status": "degraded", "stale": true,
                       "last_event_age_s": 1900.0, "gps_valid_300s": 0.05,
                       "events": [{"type": "stale", "confidence": 0.83, "reason": "..."}],
                       "note": "телеметрия устарела: последнее событие 1900 с назад"}}
```

Диспетчер видит и *почему* ТС опаздывает, и *насколько* можно доверять данным, по
которым это вычислено. Полный набор комбинаций закрыт тестом
`py ml/test_cause_selection.py`.

### Признаки (141)

- причинные телеметрические окна 60-1800 с: скорость (mean / median / std /
  p10 / p90 / доля движения / доли ниже порогов), пройденный путь, смещение GPS
- **время простоя** (`dwell_*`): длительность непрерывной серии «остановок» ≤3 км/ч,
  возраст начала простоя, доля окна в простое
- расстояние до целевой остановки, положение на маршруте
- расписание: плановые интервалы, число остановок между `T` и целью
- временные признаки с циклическим кодированием
- калибровочная производная `lead_minus_660` (отклонение от середины горизонта)

## Производительность

Замеры сделаны на том же стенде, что и обучение: 4434 точки train, 353 точки
test, 141 признак. Команда воспроизведения:
`py ml/load_test.py --concurrency 8 --requests 40`.

### Инференс

| Сценарий | p50 | p95 | Пропускная способность |
|---|---|---|---|
| 1 точка, последовательно (холодный) | 72 мс | 84 мс | 9.9 req/s |
| 1 точка, 8 параллельных (с коалесценцией) | **93 мс** | 255 мс | **65.3 req/s** |
| Батч 8 точек | 167 мс | 167 мс | 23.5 req/s |
| Все 151 точки (генерация submission) | - | - | единичная операция |

**Ключевой результат: параллельная нагрузка ускоряет систему в 6.6 раз** (9.9 → 65.3
req/s). Это прямое следствие того, что стоимость построения признаков почти не
зависит от числа строк: одна строка платит полную фиксированную стоимость (срез
расписания, телеметрии, сборка фрейма), а 50 строк - ту же самую. Микробатчинг
склеивает параллельные запросы в один вызов, и стоимость на строку падает.

### Что дало ускорение сборки признаков

`cumulative_distance` (накопленный путь по GPS) зависит только от телеметрии
автомобиля, а не от момента `T` прогнозной точки, но раньше пересчитывался
чистым Python-циклом по всей истории ТС **для каждой точки отдельно**. Стоимость
росла как `точки × история`. Сейчас телеметрия каждого `tr_id` готовится один раз
на вызов (`_prepare_vehicle_telemetry`), а причинный срез остаётся прежним -
это индекс `searchsorted(times_ns, T, "right")`, применённый позже.

| Сборка признаков на validate (151 точка) | Время |
|---|---|
| До | 13.4 с |
| После | 1.6 с (**×8.4**) |

Значения всех 140 числовых признаков при этом **бит в бит совпадают** со старой
реализацией (сверено сравнением фреймов), то есть модель и её предсказания не
изменились - выросла только скорость.

Эквивалентность батчинга при этом по-прежнему строго доказана: батчинг не меняет
предсказания ни на одну величину (тест `ml/test_batching.py` проверяет
`max abs difference = 0.0`). Обоснование: причинный срез каждой точки зависит
только от её собственного `T`, поэтому объединение запросов добавляет строки
лишь с `event_time ≤ T` - то есть ровно те наблюдения, которые были доступны этой
точке изначально.

### Вспомогательные операции

| Эндпоинт | Задержка | Размер ответа |
|---|---|---|
| `/ndtp/status` | 15 мс | 0.2 КБ |
| `/cascade` | 3 мс | 5.8 КБ |
| `/stream/status` | 29 мс | 113-409 КБ |
| `/health` | 4 мс | - |

Размер `/stream/status` зависит от позиции реплея: снимок растёт по мере того,
как в поток вступают новые ТС (от ~113 КБ на старте до ~409 КБ при 13 ТС в
кадре). Поэтому указан диапазон, а не одно число.

### Решения, давшие выигрыш

1. **Подготовка телеметрии один раз на ТС** (`_prepare_vehicle_telemetry`) -
   `cumulative_distance` и разбор кадра телеметрии вынесены из цикла по точкам,
   векторизованы; ×8.4 на сборке признаков
2. **Микробатчинг** (`src/batching.py`) - склейка параллельных запросов, окно 4 мс
3. **Мемоизация расписания** - разбор WKT через `lru_cache`, подготовка расписания
   один раз на процесс вместо каждого запроса
4. **Троттлинг live-прогнозов** - кэш по `(unit_id, event_time)` с TTL и вытеснением,
   повторные опросы статуса не пересчитывают модель

Профилировщик: `py ml/profile_inference.py` - показывает долю признаков в общем времени
и горячие места.

### Честное ограничение

Штатный режим работы дашборда - батчинг через `/stream/status`, а не поток
одиночных `/predict`: он возвращает весь снимок витрины за один вызов. При потоке
из сотен ТС с обновлением раз в 2-3 секунды одного снимка витрины на каждое
обновление недостаточно: снимок дорог по числу ТС в кадре.

Что уже сделано: стоимость признаков на точку перестала зависеть от длины
истории телеметрии (векторная подготовка вместо Python-цикла, один раз на ТС).
Что осталось следующим шагом: переиспользовать подготовленный кадр **между
вызовами** (`/stream/status` пересобирает признаки заново на каждом тике
реплея) и держать прирост инкрементально, а не пересчитывать окна целиком.

## Найдено при финальной проверке submission: потеря телеметрии на HTTP

Расхождение локального и задеплоенного прогона не было случайным шумом
численного типа. Оно воспроизводилось на **142 из 151** точек.

**Причина.** Backend отдаёт телеметрию ML-сервису в JSON. Даты сериализовались
через `Timestamp.isoformat()`, который добавляет дробную часть **только когда
она есть**. Получается колонка, где часть строк выглядит как
`2026-01-06T03:35:00`, а часть - как `2026-01-06T03:35:00.462764`.

На приёме `pd.to_datetime(series, errors="coerce")` определяет формат по первому
элементу и применяет его ко всей колонке. Строки с дробной частью становились
`NaT`, а `normalise_telemetry()` их удалял через `dropna(subset=["event_time"])`.
В validate-телеметрии **6 547 из 105 945** строк имеют субсекундную точность -
потеря была не маргинальной. Менялись `telemetry_points`, возраст последнего
события и все speed-окна, то есть менялся сам вход модели.

**Почему это не поймали тесты.** Причинность проверялась на синтетике с
целочисленными секундами - такой набор данных однороден, и баг на нём
непроявим.

**Исправлено в двух местах, оба закреплены тестом:**

| | |
|---|---|
| `src/ml_client.py::_iso` | клиент пишет один канонический вид `%Y-%m-%d %H:%M:%S.%f`, поэтому сервису не нужно угадывать |
| `ml-service/service.py::_ensure_datetime` | сервис разбирает ISO8601 и делает fallback по элементам, вместо доверия формату, выведенному из первой строки |

`py ml/test_submission_transport.py` проверяет обе стороны и главное свойство
целиком: 105 945 строк телеметрии сохраняются на пути backend → ML, и
локальный прогноз совпадает с HTTP-прогнозом по всем 151 точкам. Файлы
`submission.csv`, полученные локально и через стек, теперь побитово идентичны.


Реализовано сверх базовых требований:

**1. Каскадное распространение задержки по сети** (`src/cascade.py`)
Главная дополнительная возможность. Задержка не остаётся локальной: она
проецируется вперёд по плановой последовательности остановок и заражает
пересекающиеся маршруты. Модель - сводящийся оператор
`T(D) = max(0, λ·D − b) + n`, где `λ` - доля задержки, переживающая переход,
`b` - буфер времени, который парк может «отобрать», `n` - локальный источник
(простой на остановке). Из математики напрямую следует ответ, нужный диспетчеру:
**на какой остановке задержка полностью поглотится**. Связывание маршрутов идёт
по геометрической пересечении коридора, а не по идентификатору остановки
(идентификаторы в датасете уникальны для каждого ТС).

**2. Калиброванная вероятность опоздания**
`P(опоздание > 120 с)` вместо голой величины задержки. Brier 0.066 против 0.184.

**3. Детекторы паттернов с измеренным качеством**
Четыре детектора с честно измеренными precision/recall и явными ролями
(strong / weak / data_quality) - в UI статус сигнала показывается рядом с причиной.

**4. Приём живого потока NDTP** (`src/ndtp.py`, `src/ndtp_server.py`)
Собственная реализация протокола: разбор NPL/NPH-заголовков, CRC-16/Modbus со
свапом байтов, handshake, декодирование навигационной ячейки `G6CellNav00` и ячеек
дверей `G6CellCrown03`. Layout ячейки дверей **подтверждён живым захватом** с
эмулятора. Обрабатываются обрывы связи и переподключения.

**5. Микробатчинг с доказанной эквивалентностью**
Параллельные запросы объединяются в один вызов модели без изменения результата.

**6. Троттлинг и деградация**
Кэш live-прогнозов с вытеснением. При отсутствии расписания, модели или потока
система не падает, а возвращает явный статус (`no_schedule`, `no_model`,
`out_of_horizon`, `no_time`) с человекочитаемым пояснением на русском.

**7. Наблюдаемость**
`/metrics` с гистограммой задержек по эндпоинтам, временем инференса и
эффективностью батчинга. Заголовок `X-Response-Time-Ms` в каждом ответе.

**8. Привязка координат к маршруту (map matching)**
`src/runtime.py`, функция `snap_to_polyline`. GPS-точка проецируется на ближайший
сегмент плановой геометрии маршрута (координаты остановок из `ScheduleIndex`),
и в ответе появляется `matched_position` с исправленной точкой, сегментом,
долей прохождения сегмента и `snap_distance_m`; флаг `on_route` сравнивает
смещение с допуском 150 м. Сырая точка при этом сохраняется рядом -
диспетчер видит и реальный GPS, и положение на маршруте.
Это сознательно простая геометрия «точка → ломаная», без графа дорог и без
OSRM-уровня сопоставления; в честности данных это заявлено как map matching
первого уровня. Тест `py ml/test_map_matching.py` проверяет перпендикулярную
проекцию, зажим на концах сегмента, выбор ближайшей ветви на развилке и
деградацию на вырожденных входных данных.

**9. Автоматическая проверка целостности данных**
`ml/sanity_check.py` проверяет покрытие `submission.csv`, отсутствие будущих
наблюдений в признаках (по всем 151 точкам) и недоступность фактического времени
прибытия. Если `submission.csv` отсутствует, скрипт генерирует его сам и
проверяет результат, поэтому запускается из свежего клона одной командой.

## Честность данных и ограничения

Принципы академической честности соблюдены, и это проверяемо:

**Анти-утечка (причинность).** Телеметрия для точки прогноза `T` берётся строго
по условию `event_time ≤ T`. Реализовано поиском
`np.searchsorted(times, T, side="right")` для каждой точки отдельно -
механически исключена возможность увидеть будущее. Окна признаков привязаны к
моменту последнего известного события, а не к хвосту массива.

**Фактическое время не читается.** Колонка `time_fact_begin` не используется ни в
одном модуле: ни в признаках, ни в расписании, ни в каскаде. Проверено
статическим анализом (`ml/sanity_check.py`).

**Горизонт 10-15 минут соблюдается.** Целевая остановка выбирается строго из
планового окна `(T + 10 мин, T + 15 мин]`. Для живых юнитов цель вне горизонта
явно помечается и прогноз не выдаётся.

**Отклонение live-ТС измеряется, а не подставляется** (`src/deviation.py`).
Раньше в live-контур для каждого юнита уходил жёсткий `cur_dev_s = 0.0`, то есть
модель получала утверждение «ТС точно по графику» для 100% живых ТС. В обучающей
выборке `cur_dev_s > 120` у 26.5% точек, так что это был не нейтральный
плейсхолдер, а систематический сдвиг к «вовремя», и детектор `backlog`
(`cur_dev_s >= 120`) для live-юнитов не мог сработать никогда.

Сейчас значение = **фактическое прохождение последней доказанно пройденной
остановки минус её плановое `time_begin`**, где факт прохождения берётся из
ближайшей GPS-точки. Обе оценки антиутечки выполняются внутри функции, а не
на стороне вызова: телеметрия режется по `event_time <= T`, а из расписания
берутся только остановки с `time_begin <= T` (не пройдена та, что запланирована
после T). `time_fact_begin` не читается.

Уровни достоверности видны в ответе (`cur_dev_hint` + `cur_dev_source`):

| `cur_dev_hint` | Что означает |
|---|---|
| `measured` | остановка сопоставлена с телеметрией — измерение |
| `nearest_stop` | ТС ещё не проходила остановки; оценка по ближайшей плановой |
| `held` | измерить не удалось, показана последняя достоверная (TTL 300 с) |
| `none` | измерить нельзя; значение 0 и это **явно помечено** |

Измерение на реальном validate-периоде против ground truth из `points.csv`
(151 точка, `py ml/test_deviation.py`): MAE **137 с**, медианная ошибка **71 с**,
корреляция **+0.21**, доля точек в пределах ±300 с - **87%**. Опоздание
(`> 120` с) определяется с precision 0.54 / recall 0.68 - там, где константа
давала 0 срабатываний.

Честная оговорка: по одному только MAE константа выглядит немного лучше
(112 с против 137 с), потому что у неё нулевое разбросное отклонение. Но
константа не несёт информации вовсе (r не определён), и модель на её основе
физически не может отличить опоздавшее ТС от вовремя идущего. Перенос
отклонения с опорной остановки на текущий момент был реализован и **отклонён по
замерам**: MAE падает до 126 с и смещение выравнивается, но recall по опозданию
проседает с 0.68 до 0.12 - усреднение съедает ровно тот сигнал, ради которого
признак существует.

**Честно измеренные ограничения, а не замаскированные:**

- **Детектор `stale` не является предиктором задержки** (precision 0.0). Он вынесен
  в отдельную роль `data_quality` и используется как флаг достоверности, а не как
  причина опоздания. Публиковать его как причину было бы нечестно.
- **Детекторы `dwell` и `speed_drop` слабые** (precision ≈ базовая ставка 0.24).
  Они помечены ролью `weak_signal` и в карточке инцидента показываются с этой
  пометкой.
- **Межмаршрутная связность ограничена данными.** В validate-периоде лишь 2 из 13 ТС
  пересекаются по геометрии, а в train пересечения в основном между синтетическими ТС.
  Каскад вдоль маршрута работает на всех данных, межмаршрутное заражение - точечно.
  Это ограничение данных, а не модели, и оно зафиксировано здесь.
- **Map matching - первая ступень, не полноценный сопоставитель.** `snap_to_polyline`
  проецирует точку на ближайший сегмент плановой ломаной по координатам остановок.
  Это не HMM-сопоставление по истории трека, не граф дорог и не OSRM-уровень:
  близкие параллельные улицы в геометрии остановок различить нельзя, поэтому
  результат - индикатор положения на маршруте и флаг `on_route`, а не автотранспортная
  траектория. Уровень решения зафиксирован здесь, чтобы не выдавать его за полный
  map matching.
- **Ячейка `G6CellIrma04` не декодируется.** Все её поля помечены `BitField` без
  раскрытой битовой ширины, поэтому корректный разбор невозможен. Ячейка
  захватывается как raw-шестнадцатеричный дамп для последующего анализа.
- **GPU не используется.** Задача табличная, объём обучения 4434 строки - CatBoost
  на CPU даёт приемлемое время (обучение ≈ 30 с). Переход на GPU не дал бы выигрыша
  на этом объёме; измерение на таком масштабе нецелесообразно.
- **PyTorch не используется.** В стеке заявлен вместе с CatBoost. Ключевым
  требованием является качество на табличных данных, где градиентный бустинг на
  таблицах сильнее нейросети; CatBoost выиграл с MAE 47.4. Использование PyTorch
  без измеримого выигрыша было бы добавлением зависимости ради галочки.
  Статус: решение принято осознанно и зафиксировано.

## Тесты

```bash
py ml/test_ndtp.py          # протокол NDTP: handshake, CRC, ячейки, TCP-цикл
py ml/test_cascade.py       # математика каскада: 10 сценариев на синтектике
py ml/test_batching.py      # эквивалентность и причинность батчей (ML-пайплайн)
py ml/test_microbatch.py    # коалесценция параллельных запросов (backend)
py ml/test_ml_integration.py # Backend -> ML surface: HTTP, таймауты, деградация
py ml/test_schedule_index.py # общий модуль расписания: геометрия, WKT, индекс
py ml/test_patterns.py      # контракт детекторов паттернов
py ml/test_cause_selection.py # причина vs качество телеметрии, все комбинации
py ml/test_dwell.py         # признак времени простоя
py ml/test_map_matching.py  # проекция GPS-точки на плановый маршрут
py ml/test_deviation.py     # отклонение live-ТС от расписания + антиутечка
py ml/test_submission_transport.py # телеметрия backend -> ML без потери строк
py ml/sanity_check.py       # анти-утечка и целостность submission
```

`test_ml_integration.py` поднимает настоящий ML service в подпроцессе
(uvicorn), прогоняет через него batch-эквивалентность и причинность, а затем
проверяет все режимы отказа на маленьких stub-серверах: недоступность,
таймаут, некорректный JSON, неверную форму, `null`-прогноз, коды 500/503,
восстановление после возврата сервиса и то, что реплей переживает потерю ML.

Остальные тесты не требуют запущенных сервисов; `sanity_check.py`,
`test_deviation.py` и `test_batching.py` используют только закоммиченный
`dataset/validate/`.


Последние два требуют датасета (`dataset/validate/`, он в репозитории);
остальные работают без данных. `sanity_check.py` при отсутствии
`submission.csv` генерирует его сам, поэтому не падает на свежем клоне.

```bash
py -m pip install sphinx

```

| Файл | Содержание |
|---|---|
| `docs/conf.py` | конфигурация Sphinx (autodoc, napoleon, intersphinx) |

Исходники документации в `docs/` попадают в репозиторий, результат сборки
(`docs/_build/`) - нет.
