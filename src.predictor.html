src.predictor¶

Causal feature engineering and delay prediction for the NDTP hackathon data.

The feature builder deliberately never reads time_fact_begin. Labels are used only as the supervised target; all telemetry-derived features are cut at the forecast timestamp T.

class src.predictor.ScheduleIndex(schedule: DataFrame)[source]¶

Bases: object

Pre-computed, purely static view of the planned timetable.

The schedule never changes during inference, yet add_schedule_features() used to re-derive it on every call: parse 5 558 WKT points, sort by (tr_id, time_begin, stop_id), compute cumcount/inter-stop gaps and run a haversine per leg. That was ~40% of the total request latency for zero information gain.

Everything here is a function of the plan alone – the actual-arrival column is not even present in this subset – so hoisting it out of the request path cannot introduce leakage. The heavy work happens once per process; per-request the object only serves a merge.

Return a ScheduleIndex for schedule, building it once.

The index is memoised on the DataFrame through DataFrame.attrs so the caller does not have to thread it through every call site, and its lifetime is exactly the lifetime of the frame.
